Active Directory account lockout: set it in the right place, then prove it

A lockout policy protects accounts against brute-force attacks, but only if it actually applies. Here is where to put it, and how I verified it in six commands.

Active DirectoryGPOPowerShellWindows Server
In short
  • The password policy for domain accounts is set in a GPO linked to the domain root.
  • My values: 10 characters minimum, complexity, 42-day expiry, lockout after 5 failures for 30 minutes.
  • Proof: 5 × error 1326, then error 1909, “account locked out”.

Why lock accounts

Without a limit, an attacker can try thousands of passwords on an account. Lockout blocks the account after a few failures, so brute force becomes far too slow to succeed.

The right place: the domain root

This is the classic trap. For domain accounts, Active Directory applies the password and lockout policy only from a GPO linked to the domain root. A GPO linked to an organisational unit (OU) has no effect on these accounts. So I set these values in the Default Domain Policy:

SettingValue
Minimum length10 characters
Complexityenabled
Maximum age42 days
Lockout threshold5 failures
Lockout duration30 minutes

Other GPOs harden the workstations: automatic session lock after inactivity (whole domain) and USB storage blocking (Accounting and Sales OUs).

Check the value actually applied

What matters is the effective value, not the one you think you typed:

Get-ADDefaultDomainPasswordPolicy
# MinPasswordLength : 10   ComplexityEnabled : True   MaxPasswordAge : 42.00:00:00
# LockoutThreshold  : 5    LockoutDuration   : 00:30:00

Prove it with a test

On a test account, I ran six connection attempts against DC2 with a wrong password, from a client workstation:

for /L %i in (1,1,6) do net use \\192.168.20.12\IPC$ /user:tests.verrou@entreprise.local MauvaisMdp1

The first five attempts return error 1326 (wrong user name or password). The sixth returns error 1909: the account is locked out. On the server side, the confirmation:

Get-ADUser tests.verrou -Properties LockedOut, BadLogonCount |
  Select-Object Name, LockedOut, BadLogonCount
# LockedOut : True   BadLogonCount : 5

Unlock-ADAccount tests.verrou   # unlock after the test

Two more useful checks

  • gpresult /r /scope user on a workstation confirms that a GPO (here USB blocking) is actually received, and from which controller.
  • With DC1 shut down, nltest /dsgetdc:entreprise.local points to DC2, and klist shows the Kerberos tickets come from DC2: the replicated directory holds.
Watch out

Don't trust %LOGONSERVER%: it is set at logon and still showed DC1 while DC2 was answering.

Pitfalls and limits

  • Lockout can be abused: an attacker who knows user names can lock accounts on purpose. Threshold and duration are a trade-off between security and availability.
  • Monitoring event 4740 (account locked out) on domain controllers helps spot an attack in progress.

Key takeaway

A security GPO is only done once you have seen its effect: the right link, the effective value, then a test that deliberately triggers it.

Source: my final-year thesis, “Design and security of a company network infrastructure” (ISI Keur Massar, 2026). Measurements taken on a GNS3 and VMware lab.
