A custom Suricata rule that blocks a port scan in 6 seconds

The Emerging Threats ruleset reports scans but does not block them. I wrote a threshold rule, tested it in alert mode, then switched it to blocking, on pfSense.

SuricataIDS/IPSpfSensenmap
In short
  • Suricata runs on both firewalls, with three instances: WAN, DMZ and user LAN.
  • Rule 9000001 fires when a single source sends 20 SYN packets within 10 seconds.
  • Measured: first alert at 5 s, attacker blocked at 6 s.

Where I started

Suricata 7.0.11 is installed as a package on both pfSense nodes. The Emerging Threats Open ruleset loads about 22,570 rules, including the ET SCAN category that spots probes to database ports (3306, 1433, 5432…). But these rules only alert: a scan is seen, not stopped.

Where Suricata sits

Three instances per node: WAN (em0), DMZ and LAN_USERS (parent interface em3, carrying the VLANs). I used Legacy Mode: Suricata inspects a copy of the packets and, to block, adds the sender's address to the pf table snort2c.

Blocking is enabled only on the master's WAN instance, with Block Offenders, Kill States, source blocking, and blocking limited to drop rules. A pass list (PASS_LAB) protects the infrastructure: firewalls, external DNS, internal networks, pfsync link, WAN router.

Tip

The pass list is essential: without it, an over-sensitive rule could block your own router or DNS servers and cut the company off the Internet.

The rule

Its logic: one source, 20 SYN packets, 10 seconds. Here is that logic written in Suricata syntax:

drop tcp $EXTERNAL_NET any -> $HOME_NET any (msg:"LAB SCAN SYN rafale depuis exterieur - blocage"; \
  flags:S,12; threshold: type both, track by_src, count 20, seconds 10; \
  classtype:attempted-recon; sid:9000001; rev:2;)
  • flags:S,12 keeps only SYN packets, the start of every TCP connection, like those from nmap -sS.
  • threshold … track by_src, count 20, seconds 10 counts per source address: at 20 SYNs within 10 seconds, the rule fires.
  • classtype:attempted-recon files the alert as “Attempted Information Leak”, priority 2.

Test in two passes: alert, then block

  1. Rule in alert mode. From the Kali machine (192.168.207.164), scan the virtual public address:
nmap -Pn -sS -T3 --top-ports 100 200.100.10.4

Result: “LAB SCAN” alerts arrive a few seconds apart, alongside ET SCAN alerts (ports 1521, 1433, 5800–5820). The rule is accurate, and nothing is blocked yet.

  1. Switch the rule to drop, run the same scan again, then check the block table on the firewall:
pfctl -t snort2c -T show
   192.168.207.164

Measured: first alert about 5 seconds after launch, Kali's address blocked one second later. Slowed by the block, the scan lasted a little over 100 seconds. Unblocking is then done from the Blocks tab.

Pitfalls and limits

  • The rule counts SYN packets, not distinct ports: a very fast burst of legitimate connections could trigger it. Hence the pass list.
  • In Legacy Mode, a few packets get through before the block, because Suricata works on a copy.
  • For outbound traffic, the WAN instance only sees the firewall's translated address. To pin an incident on a workstation, you need the LAN_USERS instance, placed before NAT.
  • A restart while rules were being rewritten loaded only 15,186 of 22,569. After every change, check for rules successfully loaded on each node.
  • Sync copies the rule to the backup without restarting its instance: it has to be restarted manually. Prevention after a failover was not evaluated.

Key takeaway

A blocking rule is built in two passes: alert first, to make sure it is accurate, then block. And it is never complete without a pass list that protects your own equipment.

Source: my final-year thesis, “Design and security of a company network infrastructure” (ISI Keur Massar, 2026). Measurements taken on a GNS3 and VMware lab.
