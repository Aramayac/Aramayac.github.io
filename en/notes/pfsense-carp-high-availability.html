Two pfSense firewalls, one gateway: CARP, pfsync and a measured failover

A single firewall is a single point of failure. Here is how I built an active/passive pfSense cluster and, above all, how I measured what users actually see when the master fails.

pfSenseCARPpfsyncHigh availability
In short
  • Three building blocks: CARP shares the addresses, pfsync copies connections, XMLRPC copies the configuration.
  • Each zone has three addresses: the master's, the backup's and a virtual one, the only one used as a gateway.
  • Measured on my lab: 0 to 5 seconds of downtime depending on the scenario.

The problem

In a small business, all traffic goes through the firewall: Internet access, the public website, mail, traffic between departments. If it stops, everything stops. The Availability pillar of the CIA triad therefore calls for a second firewall that takes over without human intervention.

The idea in one picture

pfSense high availability relies on three complementary mechanisms:

  • CARP: both nodes share a virtual IP address (VIP). The master regularly announces it is alive; if the announcements stop, the backup takes over the address.
  • pfsync: the state table (open connections) is continuously copied to the backup over a dedicated link.
  • XMLRPC: the configuration (rules, NAT, virtual IPs…) is pushed from the master to the backup.

The addressing plan: three addresses per zone

This is what makes the failover invisible: servers and workstations use only the virtual address as their gateway. They never know which node is answering.

Step-by-step setup

  1. Assign the physical address of each interface on both nodes, and change the default admin password.
  2. Connect the two nodes directly with a dedicated SYNC link (172.16.0.0/30) and allow pfsync traffic on it.
  3. In System > High Avail. Sync on the master: enable pfsync on the SYNC interface, then XMLRPC sync to 172.16.0.2.
  4. In Firewall > Virtual IPs: create one CARP VIP per zone and per VLAN, 7 virtual addresses in total. The master keeps the lowest skew (0), so it is active by default.
  5. Declare the virtual addresses as gateways (DHCP, servers) and point the WAN router's port forwarding (ports 25, 80, 443) to the WAN VIP 200.100.10.4.
Tip

A dedicated switch (SW-WAN) puts the router and both firewalls on the same WAN segment: CARP needs both nodes on the same layer-2 network to hear each other.

Check: the CARP status

In Status > CARP, under normal operation, all 7 addresses are MASTER on PF-MASTER and BACKUP on PF-BACKUP. The Enter Persistent CARP Maintenance Mode button then triggers a clean failover.

Measure what users see

Showing MASTER proves nothing. So I measured the outage from a workstation in the user LAN, sending one HTTP request per second to an external site:

# one timestamped request per second
while true; do date +%T; curl -s -o /dev/null -w "%{http_code}\n" --max-time 1 http://external-site; sleep 1; done
ScenarioMeasured result
Controlled failover master → backupno request lost
Return to the master1 request lost, about 3–4 s
Hard stop of the active node4–5 s of downtime
Continuous ping to 192.168.20.2542 timeouts, then replies resume (1–5 ms)

Each test was repeated more than six times over several days, without network load. These are durations observed on a lab, not a guaranteed performance.

Pitfalls and limits

  • CARP needs three public addresses on the WAN (one per node plus a virtual one): this has to be negotiated with the ISP.
  • The 200.100.10.0/29 range is simulated in an isolated lab. In a reusable document, a documentation range (192.0.2.0/24) would be better.
  • For outbound connections to survive a failover, outbound NAT must use the WAN VIP, not a node's physical address.
  • XMLRPC copies the configuration, but some services (such as Suricata rules) still have to be restarted by hand on the backup.

Key takeaway

High availability is not declared, it is measured. An all-green dashboard says nothing about what users experience: only a repeated, timestamped test does.

Source: my final-year thesis, “Design and security of a company network infrastructure” (ISI Keur Massar, 2026). Measurements taken on a GNS3 and VMware lab.
