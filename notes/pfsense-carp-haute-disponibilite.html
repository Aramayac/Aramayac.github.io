Deux pare-feu pfSense pour une seule passerelle : CARP, pfsync et une bascule mesurée

Un pare-feu unique est un point de défaillance unique. Voici comment j'ai monté un cluster pfSense actif/passif, et surtout comment j'ai mesuré ce que voit l'utilisateur quand le maître tombe.

pfSenseCARPpfsyncHaute disponibilité
En bref
  • Trois briques : CARP partage les adresses, pfsync copie les connexions, XMLRPC copie la configuration.
  • Chaque zone a trois adresses : celle du maître, celle du secours et une adresse virtuelle, la seule utilisée comme passerelle.
  • Mesuré sur ma maquette : de 0 à 5 secondes de coupure selon le scénario.

Le problème

Dans une PME, tout le trafic passe par le pare-feu : accès Internet, publication du site web, messagerie, échanges entre services. S'il s'arrête, tout s'arrête. Le pilier « Disponibilité » de la triade CIA demande donc un second pare-feu capable de prendre le relais sans intervention humaine.

Le principe en une image

La haute disponibilité de pfSense repose sur trois mécanismes complémentaires :

  • CARP : les deux nœuds partagent une adresse IP virtuelle (VIP). Le maître annonce régulièrement qu'il est vivant ; si les annonces s'arrêtent, le secours prend l'adresse.
  • pfsync : la table d'états (les connexions en cours) est recopiée en continu vers le secours, sur un lien dédié.
  • XMLRPC : la configuration (règles, NAT, adresses virtuelles…) est poussée du maître vers le secours.

Le plan d'adressage : trois adresses par zone

C'est la règle qui rend la bascule invisible : les serveurs et les postes n'utilisent que l'adresse virtuelle comme passerelle. Ils ne savent jamais quel nœud leur répond.

La mise en œuvre, étape par étape

  1. Attribuer les adresses physiques de chaque interface sur les deux nœuds, et changer le mot de passe administrateur par défaut.
  2. Relier directement les deux nœuds par un lien SYNC dédié (172.16.0.0/30) et y autoriser le trafic pfsync.
  3. Dans System > High Avail. Sync sur le maître : activer pfsync sur l'interface SYNC, puis la synchronisation XMLRPC vers 172.16.0.2.
  4. Dans Firewall > Virtual IPs : créer une VIP de type CARP par zone et par VLAN, soit 7 adresses virtuelles. Le maître garde le skew le plus bas (0) : c'est lui qui est actif par défaut.
  5. Déclarer les adresses virtuelles comme passerelles (DHCP, serveurs) et faire pointer la translation du routeur WAN (ports 25, 80, 443) vers la VIP WAN 200.100.10.4.
Astuce

Un commutateur dédié (SW-WAN) relie le routeur et les deux pare-feu sur le même segment WAN : CARP a besoin que les deux nœuds soient dans le même réseau de niveau 2 pour s'entendre.

Vérifier : l'état CARP

Dans Status > CARP, en fonctionnement normal, les 7 adresses sont MASTER sur PF-MASTER et BACKUP sur PF-BACKUP. Le bouton Enter Persistent CARP Maintenance Mode permet ensuite de provoquer une bascule propre.

Mesurer ce que voit l'utilisateur

Afficher MASTER ne prouve rien. J'ai donc mesuré la coupure depuis un poste du LAN Utilisateurs, avec une requête HTTP par seconde vers un site externe :

# une requête par seconde, horodatée
while true; do date +%T; curl -s -o /dev/null -w "%{http_code}\n" --max-time 1 http://site-externe; sleep 1; done
ScénarioRésultat mesuré
Bascule contrôlée maître → secoursaucune requête perdue
Retour sur le maître1 requête perdue, environ 3 à 4 s
Arrêt brutal du nœud actif4 à 5 s d'interruption
Ping continu vers 192.168.20.2542 délais dépassés, puis reprise (1 à 5 ms)

Chaque essai a été répété plus de six fois, sur plusieurs jours, sans charge réseau. Ce sont des durées observées sur une maquette, pas une performance garantie.

Pièges et limites

  • CARP demande trois adresses publiques sur le WAN (une par nœud et une virtuelle) : c'est à négocier avec l'opérateur.
  • La plage 200.100.10.0/29 est simulée dans un labo isolé. Dans un document réutilisable, une plage de documentation (192.0.2.0/24) serait préférable.
  • Pour que les connexions sortantes survivent à la bascule, la NAT sortante doit utiliser la VIP WAN et non l'adresse physique d'un nœud.
  • XMLRPC copie la configuration, mais certains services (comme les règles Suricata) doivent encore être relancés à la main sur le secours.

Ce que je retiens

La haute disponibilité ne se déclare pas, elle se mesure. Un tableau tout vert ne dit rien de ce que vit l'utilisateur : seul un test horodaté, répété, le montre.

Source : mon mémoire de Licence 3, « Conception et sécurisation d'une infrastructure réseau d'entreprise » (ISI Keur Massar, 2026). Mesures réalisées sur une maquette GNS3 et VMware.
